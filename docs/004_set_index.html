📦 SET Index in ClickHouse

A set index stores the distinct values found in each data granule.

Example

CREATE TABLE orders
(
    order_id UInt64,
    country String,
    status String,
    price Float64,

    INDEX idx_status status TYPE set(10) GRANULARITY 1
)
ENGINE = MergeTree
ORDER BY order_id;

The important part is:

INDEX idx_status status TYPE set(10)

The 10 means the index can store up to 10 distinct values per granule.

How is it different from minmax?

Suppose one granule contains:

status:
Paid
Paid
Pending
Paid
Cancelled
Pending

A set index could store:

{Paid, Pending, Cancelled}

Then consider:

SELECT *
FROM orders
WHERE status = 'Refunded';

ClickHouse checks the set index:

{Paid, Pending, Cancelled}
             ↓
        Refunded ❌

Since Refunded isn't in the set, ClickHouse can skip reading that granule.

With minmax, this doesn't work well for categorical values because min/max doesn't tell you whether a particular value exists.

Why the number matters

This:

TYPE set(10)

means:

"Store the distinct values if there are at most 10 of them."

If a granule contains more than 10 distinct values, the index may become unable to provide useful filtering for that granule.

Example

set(10)

✅ Granule A: {Paid, Pending, Cancelled} → useful

❌ Granule B: {1, 2, 3, ..., 100} → too many distinct values → index is not useful

So set is particularly useful for low-cardinality columns.

Good use case

Imagine:

country
-------
IR
IR
IR
IR
TR
TR
TR

or:

status
------
Paid
Paid
Pending
Cancelled

A set index can be very effective.

Example

INDEX idx_country country TYPE set(20) GRANULARITY 1

Then:

WHERE country = 'US'

can potentially skip granules where US isn't present.

set vs minmax

Index Stores Best for
minmax minimum + maximum Dates, numbers, ranges
set distinct values Low-cardinality categorical data

A simple way to remember:

minmax → "Is the value/range possibly between min and max?"

set → "Is this exact value present?"
