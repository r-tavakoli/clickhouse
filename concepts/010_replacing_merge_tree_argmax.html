🔄 ReplacingMergeTree: argMax()

The ReplacingMergeTree doesn't automatically generate versions for us.

How do I get the latest value without using FINAL?

The key tool is argMax().

The Problem

Suppose our table contains:

customer_id status updated_at
101 Active 10:00:00.001
101 Inactive 10:00:05.200
101 Active 10:00:08.500
102 Active 11:00:00.100
102 Inactive 11:00:04.300

We want:

101 → Active
102 → Inactive

because those are the values at the latest timestamp.

argMax()

The syntax is:

argMax(value, version)

Meaning:

Return value from the row where version is maximum.

For example:

SELECT
    customer_id,
    argMax(status, updated_at) AS latest_status
FROM test_db.customer_versions_dt
GROUP BY customer_id;

For customer 101:

updated_at status
10:00:00.001 Active
10:00:05.200 Inactive
10:00:08.500 Active ← max timestamp

So:

argMax(status, updated_at)

returns:

Active

We Can Get Multiple Columns

This is where argMax() becomes really powerful.

SELECT
    customer_id,
    argMax(name, updated_at) AS name,
    argMax(country, updated_at) AS country,
    argMax(status, updated_at) AS status,
    max(updated_at) AS updated_at
FROM test_db.customer_versions_dt
GROUP BY customer_id
ORDER BY customer_id;

💡 You get the latest customer state without FINAL.

argMax() vs ROW_NUMBER()

Traditional SQL:

SELECT *
FROM
(
    SELECT
        *,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY updated_at DESC
        ) AS rn
    FROM customer_versions
)
WHERE rn = 1;

ClickHouse:

SELECT
    customer_id,
    argMax(status, updated_at)
FROM customer_versions
GROUP BY customer_id;

✅ For large analytical datasets, the second pattern is often very natural in ClickHouse because you're doing an aggregation rather than ranking every row.

But There's an Important Trap ⚠️

Suppose:

customer_id status updated_at
101 Active 10:00:00.500
101 Inactive 10:00:00.500

Which one is latest?

They have exactly the same version.

⚠️ argMax() doesn't magically know which update happened later.

This is why a timestamp alone isn't always a perfect version column.

A common solution is to have a deterministic sequence/version:

customer_id status version
101 Active 10
101 Inactive 11

Then:

argMax(status, version)

unambiguously returns Inactive.

Even Better: Use a Tuple

Here's a very useful ClickHouse trick.

You can use:

argMax(
    (name, country, status),
    (updated_at, version)
)

The second argument is a tuple used for ordering.

For example:

SELECT
    customer_id,
    argMax(
        (name, country, status),
        (updated_at, version)
    ) AS latest
FROM test_db.customer_versions_dt
GROUP BY customer_id;

Now ClickHouse compares:

(updated_at, version)

lexicographically.

So if two records have the same timestamp:

10:00:00.500, version 10
10:00:00.500, version 11  ← wins

✅ This gives us a deterministic tie-breaker.

💡 Pro Tip: Use argMax() with tuples for a robust "latest state" query pattern that doesn't require FINAL and handles edge cases gracefully.
