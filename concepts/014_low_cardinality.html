📦 LowCardinality

LowCardinality can reduce memory usage and improve query performance by encoding repeated string values as dictionary-based identifiers.

This is especially useful when working with billions of rows containing columns such as country, status, category, or payment_method.

1. The Problem

Imagine your test_db.orders table contains 100 million rows.

Your country column contains values such as:

Iran
Spain
Iraq
Lebanon
Iran
Spain
Iran
...

⚠️ The same strings appear repeatedly.

With a regular String column, ClickHouse stores string values in its column representation. Repeated strings can therefore consume more storage and processing resources than a dictionary-based representation would.

But notice something important:

100 million rows
4 distinct countries

There are millions of repetitions but only four unique values.

This is exactly the kind of situation where LowCardinality(String) may help.

2. What Is LowCardinality?

Consider this column:

country String

We can instead define it as:

country LowCardinality(String)

Conceptually, ClickHouse can represent the data using a dictionary and integer identifiers.

For example:

Conceptual example

Dictionary
ID 1 Iran
ID 2 Spain
ID 3 Iraq
ID 4 Lebanon
Conceptual encoded values
1
2
1
3
1
4
2
1

💡 Instead of repeatedly representing the full country name, the data can use dictionary identifiers. This illustrates the concept, not ClickHouse's exact on-disk encoding.

The dictionary maps identifiers back to their corresponding strings when the values are needed.

Why can this improve performance?

  • Less storage for repetitive string values in suitable datasets.
  • Less memory needed for some operations.
  • Faster grouping and comparison in some workloads because operations can work with encoded values.

⚠️ However, LowCardinality is not always faster or smaller. Its benefits depend on the number of distinct values, the column's data, and the query workload.

3. How Do You Use It?

You can create a table with LowCardinality columns directly.

For example:

CREATE TABLE test_db.orders_lc
(
    order_id UInt32,
    order_date Date,
    customer_id UInt32,
    product_id UInt32,
    category LowCardinality(String),
    country LowCardinality(String),
    payment_method LowCardinality(String),
    status LowCardinality(String),
    quantity UInt16,
    price Float64
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(order_date)
ORDER BY (order_date, customer_id);

Notice that we changed these columns:

category LowCardinality(String),
country LowCardinality(String),
payment_method LowCardinality(String),
status LowCardinality(String)

💡 We did not change order_id, customer_id, or quantity to LowCardinality, because numeric identifiers and quantities already have suitable numeric representations.

For an existing table, you can also change a column's type:

ALTER TABLE test_db.orders
MODIFY COLUMN country LowCardinality(String);

⚠️ Before modifying a large production table, consider the conversion cost and test it on a representative dataset.

4. When Should You Use LowCardinality?

A useful starting point is to compare the number of distinct values with the total number of rows.

Column Example Distinct Values Suitability
country 4–200 ✅ Often a good candidate
status 3–20 ✅ Often a good candidate
payment_method 5–30 ✅ Often a good candidate
category 10–1,000 ✅ Often worth testing
customer_name Millions ❌ A poor candidate
order_id Almost every row ❌ A poor candidate

💡 These are guidelines, not strict thresholds.

The key question is:

Does this column have relatively few distinct values compared with the number of rows?

ClickHouse documentation commonly recommends considering LowCardinality for columns with fewer than roughly 10,000 distinct values, while its benefit often diminishes as cardinality rises. Benchmark your actual workload rather than treating that number as a hard cutoff.

5. Today's System-Table Exercise

We can use system.columns to inspect your table's column types.

SELECT
    database,
    table,
    name AS column_name,
    type
FROM system.columns
WHERE database = 'test_db'
  AND table = 'orders'
ORDER BY position;

Next, let's estimate the cardinality of your candidate columns:

SELECT
    count() AS total_rows,
    uniqExact(country) AS distinct_countries,
    uniqExact(status) AS distinct_statuses,
    uniqExact(category) AS distinct_categories,
    uniqExact(payment_method) AS distinct_payment_methods
FROM test_db.orders;

⚠️ uniqExact calculates exact distinct counts, which can itself be expensive on very large datasets. For a quick exploratory estimate, you can use uniq instead.

Summary

Concept Description
LowCardinality(String) Dictionary-encoded string column for repeated values
Best for Columns with few distinct values relative to total rows
Avoid for High-cardinality columns (IDs, names, unique values)
Conversion Use ALTER TABLE ... MODIFY COLUMN — test first
Cardinality check Use uniqExact() or uniq() to estimate distinct counts

💡 Key Takeaway: LowCardinality is a powerful optimization for repetitive string columns, but it's not a silver bullet. Always benchmark your actual workload.
