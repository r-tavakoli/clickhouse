🔄 ReplacingMergeTree

Suppose we have:

customer_id | name  | status | version
------------|-------|--------|--------
101         | John  | Active | 1

Later John changes his status:

101 | John | Inactive | 2

With a normal MergeTree, both rows exist.

With:

ENGINE = ReplacingMergeTree(version)
ORDER BY customer_id

ClickHouse can eventually identify:

customer_id = 101

as the same logical row and keep the row with the highest:

version = 2

So conceptually:

INSERT version 1 ↓ INSERT version 2 ↓ both may temporarily exist ↓ background merge ↓ version 2 remains

The key word is: Eventually

The replacement doesn't necessarily happen immediately after the INSERT.

⚠️ This is where FINAL comes in

Suppose you insert:

INSERT INTO users VALUES
(101, 'John', 'Active', 1);

INSERT INTO users VALUES
(101, 'John', 'Inactive', 2);

Before the merge happens, this query:

SELECT *
FROM users
WHERE customer_id = 101;

may see both versions.

But:

SELECT *
FROM users FINAL
WHERE customer_id = 101;

asks ClickHouse to apply the ReplacingMergeTree logic during the query.

Conceptually:

Without FINAL

version 1 ──┐
             ├── returned
version 2 ──┘

With FINAL

version 1 ──┐
             ├── deduplicate → version 2
version 2 ──┘

🚨 Why shouldn't we always use FINAL?

Because FINAL can require additional processing at query time.

On a huge table:

1 billion rows
      ↓
SELECT ... FINAL
      ↓
deduplication work
      ↓
CPU / memory / I/O

🚨 So don't think:

"ReplacingMergeTree means I should always use FINAL."

💡 Instead:

Use FINAL when query-time correctness requires seeing the deduplicated/latest state and the underlying merges cannot be relied upon to have completed.

And for large analytical queries, you should carefully consider its cost.

Key Takeaways

Aspect Explanation
ReplacingMergeTree Keeps only the latest version (by version column) after merges
Eventually Replacement happens during background merges, not immediately
FINAL Forces deduplication at query time — can be expensive
Best Practice Use FINAL sparingly; rely on merges when possible
