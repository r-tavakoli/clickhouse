🔍 Bloom Filter Index in ClickHouse

A Bloom filter index is a probabilistic data structure that helps ClickHouse quickly determine whether a value might exist within a data granule. It's particularly valuable for "needle in a haystack" scenarios where you're searching for rare values across a large dataset.

Key Concept: Unlike minmax (which tracks ranges) or set (which stores exact distinct values), a Bloom filter uses a probabilistic approach that trades a tiny risk of false positives for significant memory savings — especially useful for high-cardinality columns.

How It Works

Think of a Bloom filter as a compact "checklist" for each granule:

  • Stores: A bit array and multiple hash functions
  • Check: "Has this value ever been seen in this granule?"
  • Answer: Either "definitely NO" (skip the granule) or "probably YES" (read the granule)

💡 Probabilistic Nature: Bloom filters can produce false positives (saying a value exists when it doesn't), causing some unnecessary reads. However, they never produce false negatives — they will never skip a granule that actually contains the value.

Syntax & Usage

INDEX index_name column_name TYPE bloom_filter([false_positive_rate]) GRANULARITY N

The false_positive_rate parameter is optional — it controls the trade-off between memory usage and accuracy.

Example

CREATE TABLE events
(
    event_id UInt64,
    user_id UInt64,
    event_type String,
    value Float64,

    INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 3
)
ENGINE = MergeTree
ORDER BY event_id;

Here:

  • 0.01 = 1% false positive rate (default is 0.025 or 2.5%)
  • GRANULARITY 3 = one index entry covers 3 table granules (3 × 8192 rows by default)

Performance Impact

A real-world example shows the dramatic difference a Bloom filter can make:

Scenario Data Scanned Query Time
Without Bloom Filter 110 million rows (9.68 GB) ~0.5 seconds
With Bloom Filter (GRANULARITY 3) 5.41 million rows (475 MB) — ~20x less data! ~0.06 seconds — ~8x faster!

✅ Best Use Cases:

  • Looking up rare values (like error codes, specific user IDs)
  • Filtering on high-cardinality columns that aren't in the sort key
  • Equality checks and IN membership queries
  • Array membership: WHERE has(array_column, value) with bloom_filter on the array column

Bloom Filter vs Other Indexes

Index Type Stores Best For Cardinality
minmax min + max values Range queries (dates, numbers) Any
set(N) Exact distinct values (up to N) Low-cardinality categorical data Low per granule
bloom_filter Probabilistic bit array "Needle in haystack" equality checks High cardinality

Simple Rule of Thumb:

minmax → "Is the value within this range?"

set → "Is this exact value present?" (when there are few distinct values)

bloom_filter → "Is this exact value present?" (when there are many distinct values)

Important Considerations

✅ When to Use

  • Searching for values that appear sparsely within granules
  • Columns with high overall cardinality but where values are concentrated within specific granules
  • Log analysis looking for specific error codes or IDs
  • Non-primary key columns that are frequently filtered by equality

❌ When to Avoid

  • Most granules already contain at least one match (no pruning benefit)
  • Extremely low-cardinality columns (where set would work better and with no false positives)
  • Queries that are always highly selective across all granules

⚙️ Tuning Tip: The GRANULARITY parameter is critical. A value that's too high creates larger index entries that may not prune effectively; too low creates more overhead. Test with EXPLAIN indexes = 1 to verify your index is actually being used.
