🧠 The ClickHouse Indexing Mindset

The problem

Suppose your table is:

CREATE TABLE orders
(
    order_id UInt64,
    customer_id UInt64,
    order_date Date,
    category String,
    quantity UInt32,
    price Float64,
    country String,
    status String
)
ENGINE = MergeTree()
ORDER BY (order_date, customer_id);

Imagine: 10 billion rows

Your sorting key is: (order_date, customer_id)

So this query can potentially benefit greatly:

WHERE order_date >= today() - 7

But what about:

WHERE country = 'France'

country isn't part of the sorting key. If France appears throughout the table, the primary index can't efficiently eliminate many granules.

⭐ The most important question

Don't ask:

"Can I create an index on country?"

Ask:

"Can this index eliminate enough granules to justify its cost?"

That's the ClickHouse mindset.

Data-Skipping Indexes in ClickHouse

A data-skipping index stores small summaries about blocks/granules of data.

Conceptually:

Granule 1 → countries: US, UK
Granule 2 → countries: Germany, France
Granule 3 → countries: US, France
Granule 4 → countries: Japan, Korea

Query:

WHERE country = 'France'

ClickHouse can potentially say:

Granule 1 → France impossible → SKIP
Granule 2 → France possible → READ
Granule 3 → France possible → READ
Granule 4 → France impossible → SKIP

That's the key idea:

The index doesn't find the rows. It tells ClickHouse which granules can be skipped.

Most important index types

Index Best for
minmax Numeric/date ranges
set Low/medium-cardinality values within granules
bloom_filter Membership checks, especially strings
tokenbf_v1 / ngrambf_v1 Text/token searches
