🔀 Projections vs Materialized Views

Projections let ClickHouse maintain alternative physical representations of a table's data, while Materialized Views let us build a separate data-processing pipeline.

Both can reduce query costs, but they solve different problems.

1. The Problem

Imagine your test_db.orders table contains billions of rows.

Your table is ordered by:

ORDER BY (order_date, customer_id)

This works well for queries filtering by date, such as:

SELECT *
FROM test_db.orders
WHERE order_date >= '2026-01-01'
  AND order_date < '2026-02-01';

But what happens when analysts frequently filter by product_id?

SELECT
    product_id,
    count() AS orders
FROM test_db.orders
WHERE product_id = 100
GROUP BY product_id;

Because product_id isn't part of the sorting key, ClickHouse might need to read many more rows than we'd like.

💡 We have two possible approaches:

  • Projection: maintain an alternative data layout that can help the optimizer execute the query more efficiently.
  • Materialized View: build a separate table containing precomputed results or transformed data.

The right choice depends on what the workload needs.

2. Projection — An Alternative Data Layout

A projection is stored as part of the source table's data parts. It can maintain a different sorting order or a pre-aggregated representation.

For example, create a projection optimized for filtering by product:

ALTER TABLE test_db.orders
ADD PROJECTION IF NOT EXISTS projection_by_product
(
    SELECT *
    ORDER BY (product_id, order_date)
);

For existing data, you can materialize it:

ALTER TABLE test_db.orders
MATERIALIZE PROJECTION projection_by_product;

Now the projection provides an alternative ordering:

Original table:
ORDER BY (order_date, customer_id)

Projection:
ORDER BY (product_id, order_date)

When a query is compatible with this layout, ClickHouse may automatically select the projection.

You can still query the original table:

SELECT
    product_id,
    count() AS orders
FROM test_db.orders
WHERE product_id = 100
GROUP BY product_id;

You generally don't need to query the projection by name.

⚠️ Important: A projection doesn't guarantee faster execution. It consumes additional storage, and the optimizer decides whether using it is beneficial. Always inspect the query plan and benchmark the result.

3. Projection Can Also Pre-Aggregate Data

Projections aren't limited to alternative sorting orders. They can also store aggregated representations.

For example:

ALTER TABLE test_db.orders
ADD PROJECTION IF NOT EXISTS projection_country_count
(
    SELECT
        country,
        count() AS order_count
    GROUP BY country
);

This projection maintains a representation of order counts by country.

A query such as:

SELECT
    country,
    count() AS order_count
FROM test_db.orders
GROUP BY country;

may be able to use that representation instead of aggregating all the raw rows.

⚠️ However, the optimizer must determine that the projection can correctly answer the query. More complicated expressions or different aggregation requirements may prevent its use.

Think of this as:

Raw orders │ Projection │ Alternative sorting order │ Pre-aggregated representation │ Optimized query execution

4. Materialized View — A Separate Data Pipeline

Suppose a dashboard repeatedly needs:

  • Daily revenue by country.
  • Number of valid orders.
  • Number of unique customers.
  • No cancelled orders.

Instead of repeatedly aggregating billions of raw rows, we can create a separate target table and populate it through an incremental Materialized View.

The architecture looks like this:

orders INSERT Materialized View Transform and aggregate AggregatingMergeTree target READ Dashboard

For example, the target table can store:

CREATE TABLE test_db.daily_country_sales
(
    order_date Date,
    country String,
    revenue AggregateFunction(sum, Float64),
    orders AggregateFunction(count),
    customers AggregateFunction(uniq, UInt32)
)
ENGINE = AggregatingMergeTree()
ORDER BY (order_date, country);

The Materialized View calculates aggregate states as data is inserted:

CREATE MATERIALIZED VIEW test_db.daily_country_sales_view
TO test_db.daily_country_sales
AS
SELECT
    order_date,
    country,
    sumState(quantity * price) AS revenue,
    countState() AS orders,
    uniqState(customer_id) AS customers
FROM test_db.orders
WHERE status != 'Cancelled'
GROUP BY
    order_date,
    country;

You then query the target table using the matching merge functions:

SELECT
    order_date,
    country,
    sumMerge(revenue) AS revenue,
    countMerge(orders) AS orders,
    uniqMerge(customers) AS unique_customers
FROM test_db.daily_country_sales
GROUP BY
    order_date,
    country
ORDER BY
    order_date,
    country;

✅ The advantage is that the dashboard queries a much smaller, pre-aggregated dataset.

⚠️ Note: an incremental Materialized View processes new inserts, not arbitrary changes to previously inserted source rows. Existing historical data generally requires a backfill.

5. Projection vs. Materialized View — The Key Differences

Feature Projection Incremental Materialized View
Main purpose Optimize queries against a source table Maintain a transformed dataset
Storage Within source table data parts Separate target table
Different sort order ✅ Yes ✅ Yes, through target table
Pre-aggregation ✅ Yes ✅ Yes
Query optimizer Can choose it automatically Typically query the target explicitly
Custom filtering and transformation More limited Flexible SELECT logic
Historical data Materialize projection for existing parts Backfill target separately
Storage overhead Additional storage Additional storage
Typical use case Make existing queries faster Build a dashboard-ready summary

A useful rule of thumb:

Choose a Projection when you want to improve the execution of queries against an existing table without changing the query interface.

Choose a Materialized View when you want to maintain a separately modeled, transformed, or aggregated dataset.

💡 These are guidelines rather than absolute rules; both features can support pre-aggregation.

6. How Do You Verify Whether a Projection Is Used?

⚠️ Don't assume that creating a projection means ClickHouse will use it.

First, inspect the available projections:

SELECT
    database,
    table,
    name,
    type,
    sorting_key
FROM system.projections
WHERE database = 'test_db';

Next, inspect the query plan:

EXPLAIN indexes = 1
SELECT
    country,
    count()
FROM test_db.orders
GROUP BY country;

Look for evidence that a projection is selected. The exact output depends on the ClickHouse version and query.

You can also compare query performance with projections enabled and disabled:

SELECT
    country,
    count()
FROM test_db.orders
GROUP BY country
SETTINGS optimize_use_projections = 0;

Compare this with the same query using the default setting. Check execution time and read_rows in system.query_log, and make sure both queries return the same results.

Summary

Concept Description
Projection Alternative physical representation stored within source table parts
Materialized View Separate pipeline that transforms inserts into a target table
Optimizer Automatically selects projections; MVs are queried explicitly
Verification Use system.projections, EXPLAIN, and system.query_log

💡 Key Takeaway: Use projections to accelerate queries on the same table without changing your SQL. Use Materialized Views to build separate, transformed datasets — especially for dashboards.
