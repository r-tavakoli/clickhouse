🔗 Materialized Views in ClickHouse

✅ Materialized Views can automatically populate our aggregate table whenever new data is inserted.

1. The Problem

Imagine new orders arrive continuously:

10:00 → 100,000 orders
10:01 → 100,000 orders
10:02 → 100,000 orders
...

We don't want to repeatedly run a huge aggregation query.

Instead:

orders │ INSERT ▼ Materialized View ▼ AggregatingMergeTree ▼ Dashboard

The Materialized View processes the incoming insert automatically.

2. Create a Target Table

Suppose we have this table:

DROP TABLE IF EXISTS test_db.daily_country_sales_mv;

CREATE TABLE test_db.daily_country_sales_mv
(
    order_date Date,
    country String,
    revenue AggregateFunction(sum, Float64),
    orders AggregateFunction(count),
    customers AggregateFunction(uniq, UInt32)
)
ENGINE = AggregatingMergeTree()
ORDER BY (order_date, country);

We are storing:

  • revenue
  • order count
  • unique customer count

as aggregate states.

3. Create the Materialized View

CREATE MATERIALIZED VIEW test_db.daily_country_sales_view
TO test_db.daily_country_sales_mv
AS
SELECT
    order_date,
    country,
    sumState(quantity * price) AS revenue,
    countState() AS orders,
    uniqState(customer_id) AS customers
FROM test_db.orders
WHERE status != 'Cancelled'
GROUP BY
    order_date,
    country;

The important part is:

TO test_db.daily_country_sales_mv

This tells ClickHouse:

Put the result of this Materialized View into this target table.

4. What Happens Now?

Suppose you insert:

orders ↓ INSERT ↓ Materialized View executes ↓ GROUP BY country/date ↓ aggregate states ↓ daily_country_sales_mv

✅ You don't have to manually populate the aggregate table for future inserts.

That's the big advantage.

5. Query the Result

SELECT
    order_date,
    country,
    sumMerge(revenue) AS revenue,
    countMerge(orders) AS orders,
    uniqMerge(customers) AS customers
FROM test_db.daily_country_sales_mv
GROUP BY
    order_date,
    country
ORDER BY
    order_date,
    country;

Notice the pattern:

INSERT side SELECT side
sumState() → sumMerge()
countState() → countMerge()
uniqState() → uniqMerge()

💡 This pattern is extremely important in ClickHouse.

6. ⚠️ A Very Important Materialized View Behavior

This catches many people.

Suppose orders already contains:

10 million rows

and then you create:

CREATE MATERIALIZED VIEW ...

⚠️ The Materialized View does not automatically process those existing 10 million rows.

It normally processes new inserts that happen after the view is created.

So if you want to populate the target table with historical data, you typically do:

INSERT INTO test_db.daily_country_sales_mv
SELECT
    order_date,
    country,
    sumState(quantity * price),
    countState(),
    uniqState(customer_id)
FROM test_db.orders
WHERE status != 'Cancelled'
GROUP BY
    order_date,
    country;

Then the Materialized View handles future inserts.

This distinction is important:

Existing data ↓ manual backfill
New data ↓ Materialized View

7. Materialized View ≠ Normal Database View

A normal view:

CREATE VIEW ...

basically stores a query.

When you query it:

SELECT ↓ execute underlying query ↓ calculate result

A Materialized View can store the transformed result in a target table.

So:

Normal View:

query → raw data → calculate → result

Materialized View:

INSERT → transform → store
                       ↓
                    query
                       ↓
                  small dataset

✅ This is why Materialized Views can be extremely useful for dashboards.

Summary

Concept Description
Materialized View Automatically transforms incoming inserts and stores results
TO target_table Specifies where the Materialized View writes its output
State → Merge pattern sumState → sumMerge, countState → countMerge, etc.
Historical data Must be backfilled manually with an INSERT ... SELECT
Normal View vs Materialized View Normal view calculates on read; Materialized View stores results
system.dependencies Shows relationships between tables and views

💡 Key Takeaway: Materialized Views + AggregatingMergeTree = automatic, continuous pre-aggregation for real-time dashboards.
