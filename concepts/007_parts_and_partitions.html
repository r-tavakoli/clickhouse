📁 Parts & Partitions in ClickHouse

One of the biggest differences between ClickHouse and traditional OLTP databases is how it stores inserted data.

In ClickHouse, an insert does not immediately create one big table file.

Instead:

INSERT ↓ New Part ↓ Background Merge ↓ Larger Part

A part is a physical chunk of data stored on disk.

Example

You insert:

INSERT INTO orders VALUES (...)

ClickHouse creates:

orders/
 ├── part_1
 ├── part_2
 ├── part_3

After background merging:

orders/
 └── part_1_2_3

The data is combined.

Why Does ClickHouse Do This?

Because ClickHouse is optimized for:

  • huge inserts
  • analytical queries
  • immutable data

Instead of updating rows constantly, it writes new parts and later merges them.

⚠️ This is why: Many small inserts are bad.

Example of a Bad Ingestion Pattern

Imagine:

for row in million_rows:
    INSERT row

You might create:

part_1
part_2
part_3
...
part_100000

Now ClickHouse has a problem:

  • too many files
  • too many merges
  • slower queries
  • high CPU usage

This is called:

Too many parts problem

Parts vs Partitions

Partition

Logical data separation:

PARTITION BY toYYYYMM(order_date)

Example:

202501
202502
202503

Used for:

  • dropping old data
  • partition pruning

Part

Physical storage unit.

Example:

Partition 202501
    |
    +-- part_001
    +-- part_002
    +-- part_003

A partition can contain many parts.

Think:

Table
 |
 +-- Partition 202501
 |        |
 |        +-- Part A
 |        +-- Part B
 |
 +-- Partition 202502
          |
          +-- Part C

Active Parts

What does active mean?

From system.parts:

active = 1

means:

This part is currently used by queries.

Example:

part_001  active=1

Normal.

active = 0

means:

Old part, no longer used, waiting for cleanup.

Example:

Before merge:

part_001 active=1
part_002 active=1

After merge:

part_003 active=1   <-- new merged part

part_001 active=0
part_002 active=0

Eventually ClickHouse removes inactive parts.
