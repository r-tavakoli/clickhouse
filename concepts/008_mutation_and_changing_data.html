🔄 Mutations & Changing Data in ClickHouse

What happens when we actually want to UPDATE or DELETE data?

🧠 1. Concept — Mutations

In a traditional database, we might do:

UPDATE orders
SET status = 'Paid'
WHERE order_id = 100;

and expect the existing row to be modified.

In ClickHouse, this is fundamentally different.

ClickHouse is optimized around immutable data parts.

So an UPDATE is generally implemented as a mutation.

Conceptually:

Existing part ↓ read affected data ↓ rewrite part ↓ new part ↓ old part eventually removed

⚠️ That's why updates can be expensive.

Example

Suppose:

UPDATE test_db.orders
SET status = 'Paid'
WHERE order_id = 100;

ClickHouse doesn't simply find one row and overwrite a few bytes.

It may need to rewrite the affected data in the relevant parts.

For a huge table:

1 billion rows
       ↓
UPDATE 1 row
       ↓
potentially expensive

💡 This is one reason ClickHouse isn't designed to behave like an OLTP database.

How to Run an UPDATE

The syntax is:

ALTER TABLE test_db.orders
UPDATE status = 'Paid'
WHERE order_id = 100;

Notice:

ALTER TABLE
    ↓
UPDATE

This is a mutation.

Similarly, deleting:

ALTER TABLE test_db.orders
DELETE
WHERE order_id = 100;

is also a mutation.

Key Takeaways

Concept Traditional Database ClickHouse
UPDATE In-place row modification Mutation — rewrites parts
DELETE In-place row deletion Mutation — rewrites parts
Performance Fast for single rows Can be expensive; designed for batch operations
Syntax UPDATE ... SET ... ALTER TABLE ... UPDATE ...

Remember: ClickHouse is optimized for append-heavy workloads. Mutations are possible but should be used sparingly and in batch.
