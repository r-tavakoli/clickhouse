📊 Projections in ClickHouse

A projection is essentially an additional physical representation of a table's data, stored in a way that can make certain queries much faster.

Think of it like this:

Original table
     │
     ├── normal data
     │
     └── projection
           │
           └── data organized differently

💡 Key Insight: Projections give you the power to have multiple physical layouts for the same logical table, each optimized for different query patterns.

When Do You Need a Projection?

Suppose your table is:

ORDER BY (order_date, customer_id)

This is excellent for:

WHERE order_date >= ...

But suppose you frequently run:

SELECT
    country,
    count()
FROM orders
GROUP BY country;

Your table isn't organized around country.

A projection can provide another physical layout optimized for that workload.

Simple Example

ALTER TABLE test_db.orders
ADD PROJECTION country_projection
(
    SELECT
        country,
        count()
    GROUP BY country
);

Conceptually, ClickHouse can maintain an additional representation containing the information needed for that query.

Then ClickHouse's optimizer can decide:

"The projection is cheaper than reading the main table, so I'll use it."

That's the important difference from manually creating another table.

Projection vs Data-Skipping Index

Data-Skipping Index

Answers: "Can I skip this granule?"

For example:

country = 'IR'
       ↓
Can I skip this granule?

It doesn't contain a replacement copy of the table.

Projection

Answers: "Can I answer this query more efficiently using another physical representation?"

For example:

Original table
ORDER BY order_date

Projection
GROUP BY country

The projection can potentially provide the data in a much more efficient form for that query.

⚠️ Projection Isn't Free

A projection means ClickHouse has additional data to maintain.

Therefore:

INSERT
  ↓
main table
  +
projection

And during merges, the projection also needs maintenance.

⚠️ So don't create projections for every query.

Think: frequent + expensive query pattern → possible projection candidate

What Projections Do

Use Case How It Helps
Queries on non-primary key columns Data is reordered by the column you frequently filter on, making it faster
Pre-aggregated queries Stores pre-computed GROUP BY results, reducing both computation and I/O
Multiple filters in one query Multiple lightweight projections can work together to prune data at the granule level

⚙️ How Projections Work

  • Physically stored alongside the main table – They appear as hidden tables, so you don't need to change your queries.
  • Automatically selected by the query optimizer – ClickHouse decides whether to use a projection without you having to modify your SQL.
  • Asynchronously updated – When you insert new data, projections update in the background.

🆚 Projections vs. Materialized Views

Aspect Projections Materialized Views
Query interaction ✅ Automatic and transparent Requires querying the target table directly
Data storage ✅ Stored with the main table (hidden) Stored in a separate, explicit target table
JOIN support ❌ Not supported in projection definitions ✅ Supported (refreshable MVs)
WHERE clause in definition ❌ Not supported ✅ Supported
Operational overhead ✅ Lower (automatic maintenance) Higher (manual backfilling, target table management)
Applicable engines Only MergeTree family Various source table engines

💡 Pro Tip: Projections are often the simpler choice when you just need to optimize queries within the same table. Materialized views are better when you need JOINs, filters in the definition, or want to expose the pre-aggregated data as a separate table.
