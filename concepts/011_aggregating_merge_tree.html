📊 AggregatingMergeTree in ClickHouse

1. The Problem

Imagine we have 10 billion orders:

order_id
customer_id
country
amount
order_date

And our dashboard constantly asks:

"How much revenue did we make per country per day?"

If we repeatedly run:

SELECT
    order_date,
    country,
    sum(amount)
FROM orders
GROUP BY order_date, country;

ClickHouse has to aggregate potentially billions of rows every time.

💡 Instead, we can maintain pre-aggregated states.

That's where AggregatingMergeTree comes in.

2. AggregatingMergeTree

Basic idea:

10 billion raw orders ↓ aggregation ↓ much smaller aggregate table ↓ dashboard queries

Example target table:

CREATE TABLE test_db.daily_country_sales
(
    order_date Date,
    country String,

    revenue AggregateFunction(sum, Float64),
    orders AggregateFunction(count)
)
ENGINE = AggregatingMergeTree()
ORDER BY (order_date, country);

Notice these aren't normal:

sum(...)
count(...)

Instead:

AggregateFunction(sum, Float64)
AggregateFunction(count)

These columns store aggregate states, not finalized numbers.

3. sumState() and sumMerge()

This is the key concept today.

When inserting into the aggregate table:

sumState(amount)

creates a sum state.

When reading:

sumMerge(revenue)

merges those states and gives you the actual result.

Think:

sumState() ↓ stores intermediate aggregation state ↓ sumMerge() ↓ final number

Similarly:

countState()
     ↓
countMerge()

4. Example

Suppose raw orders are:

date country amount
2026-09-10US100
2026-09-10US200
2026-09-10IR150
2026-09-10US50

We could insert aggregate states:

INSERT INTO test_db.daily_country_sales
SELECT
    order_date,
    country,
    sumState(amount),
    countState()
FROM test_db.orders
GROUP BY
    order_date,
    country;

Then query:

SELECT
    order_date,
    country,
    sumMerge(revenue) AS revenue,
    countMerge(orders) AS orders
FROM test_db.daily_country_sales
GROUP BY
    order_date,
    country
ORDER BY
    order_date,
    country;

Result:

date country revenue orders
2026-09-10IR1501
2026-09-10US3503

5. Why Not Just Use MergeTree?

You could create:

CREATE TABLE daily_country_sales
(
    order_date Date,
    country String,
    revenue Float64,
    orders UInt64
)
ENGINE = MergeTree()
ORDER BY (order_date, country);

But AggregatingMergeTree is designed specifically for storing aggregate states that can be merged.

This becomes particularly powerful when combined with:

Materialized Views
Raw orders ↓ Materialized View ↓ AggregatingMergeTree ↓ Dashboard

6. ⚠️ Very Important: AggregatingMergeTree Doesn't Magically Aggregate Your Data

This is a common misunderstanding.

Creating:

ENGINE = AggregatingMergeTree()

doesn't mean:

"ClickHouse will automatically aggregate everything."

You need to insert aggregate states:

sumState()
countState()
uniqState()
argMaxState()

and retrieve them using:

sumMerge()
countMerge()
uniqMerge()
argMaxMerge()

⚠️ Remember: AggregatingMergeTree stores states, not final values. You must use the State and Merge combinators.

Summary

Concept Description
AggregatingMergeTree Stores pre-aggregated states, not raw rows
sumState() Creates an intermediate sum state during INSERT
sumMerge() Merges sum states and returns the final value during SELECT
AggregateFunction(type, ...) Special column type for storing aggregate states
system.columns Use to verify aggregate state column types

💡 Key Takeaway: AggregatingMergeTree + Materialized Views = a powerful pre-aggregation pipeline that dramatically speeds up dashboard queries on massive datasets.
